# 界面用语表

> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> **本文是自足的**：不引用任何其他技能或外部文档。

## 为什么有这张表

同一个东西有四个名字，各管一段：

- **契约用语**：写文档、讨论设计时用的词。
- **描述文件里的 key**：机器读的字段名，ASCII、稳定、进错误消息与测试断言。
- **界面上的说法（中文）**：使用者在图上看到的字。**MUST 是大白话，刚入行的人不需要任何背景知识就能看懂。**
- **界面上的说法（英文）**：`--lang en` 出图时看到的字。**同一条大白话判据照样适用**——
  英文那套 MUST NOT 用 node / edge / payload 这类术语，把中文这边好不容易避开的坑再踩一遍。

四者一一对应，**MUST NOT 在这四套之外再造第五个说法**。

**描述文件里的正文不在这张表的管辖范围内**：方块名、职责、信息的一句话说明都是被分析项目
自己的话，`--lang en` 也 **MUST NOT 翻译**——翻了就不是事实了。这张表只管框架文案。

## 四条硬规矩

1. **载体取值 `bundle` 在界面上 MUST 写「一份打包好的数据」**，MUST NOT 写成「结构体」这类技术词。
2. **专有名词保留原词，但 MUST 在旁边给一句白话解释**：`MCP` 写成「外挂的能力（MCP）」，`Skill` 写成「装的技能（Skill）」。
3. **标识符 MUST NOT 翻译**——这是唯一的例外，且是硬性的：

   `tools` / `mcp` / `skills` 数组里的每个字符串（如 `read`、`grep`、`agent_fs`、`todo_write`、`write`）、`system_prompt.file` 的文件名、`source.refs` 里的路径与函数名，一律**原样照抄**。

   **为什么**：这些是使用者要拿去在代码里搜的字符串。译成中文之后就搜不到了，也对不上项目里的实际配置。

4. **`--lang en` MUST NOT 翻译描述文件里的正文**——方块名、职责、信息的一句话说明、组成、时机，
   一律原样呈现。它们是被分析项目自己的话，翻过一道就成了转述，图也就不再是事实。

## 判据

界面上出现的每个词，MUST 能被一个刚接触 agent 开发的人直接读懂。**需要先解释一遍才能理解的浓缩术语 MUST NOT 出现在界面里。**

自查方法：把渲染出来的 HTML 剥掉 `<style>` 与 `<script type="application/json">` 之后——

- **中文界面**正文里 MUST NOT 出现「节点」「边」「传递物」「并发数」「可信度」「载体」「结构体」「实体」「字段」这几个词。
  前七个是现行清单，**MUST 全量保留、只增不减**；后两个是这次随信息块一起追加的——
  「信息实体」「字段」正是最容易顺手写进新界面的两个术语。
- **英文界面**正文里 MUST NOT 出现 `node`、`edge`、`payload`、`carrier`、`entity`、`field`、
  `struct`、`concurrency`、`confidence` 这几个词。它们与上面那份中文清单一一对应，
  是同一条判据的英文投影，**MUST NOT 只顾中文那边**。

两份清单都只查框架文案。描述文件里的正文照原样出现，不受此限——
被分析项目的代码里本来就可能写着 `payload`，那是事实，不是界面用语。
