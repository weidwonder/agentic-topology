# 节点粒度约定

> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> **本文是自足的**：不引用任何其他技能或外部文档。

## 为什么必须先定这个

不定粒度，节点数就不可复核——换个人重跑同一个模块会得到不同的数，两张图没法比对，"遗漏为 0"也就无从谈起。

## 判据

> **一个节点 = 编排上一个可独立指认的处理环节。**
> 判据是：**它有自己的输入与输出，且上下游能明确指向它。**

据此展开成四条可操作的规则：

| # | 情形 | 怎么切 |
|---|---|---|
| 1 | 同一个函数里顺序执行、外部无法单独指认的若干步 | **合成一个节点** |
| 2 | 被复用同一会话追加一轮的调用 | **不算新节点**。怎么表达见下方〈同会话追轮怎么画〉 |
| 3 | 纯观测、只写日志、不改变数据流的旁路 | **不算节点** |
| 4 | 拆到什么程度算够 | 拆到**再拆下去就没有独立输入输出**为止 |

## 三类执行者怎么分

| 类型 | key | 什么算这一类 |
|---|---|---|
| Agent | `agent` | 一次模型会话。**判据是「装配了一套系统提示词」**——**系统提示词变了才是另一个 Agent**；换 provider、换模型、换用户消息都只是**同一个本体的不同参数**，仍是同一个节点。见下方〈到底看哪一段来分 Agent〉 |
| 程序 | `program` | 确定性代码：读写文件、算指纹、校验、调度、渲染、对账 |
| 判断 | `decision` | 一个显式的分岔点：按某个条件决定往哪走。**内联在程序里、外部指认不出来的 if 不单独成节点**（规则 1） |

## 切法 MUST 可复现：按这个顺序机械地做

上面四条规则回答的是"这算不算一个节点"，但**不回答"从哪儿开始找候选"**。
不定这一步，两次抽取会从不同的地方起手，切出不同的节点集——实测已经发生过。
所以候选边界 MUST 按下面这个顺序**从源码里机械地枚举**，MUST NOT 凭对业务的理解直接下笔：

1. **枚举候选边界**：源码里每一处「产生了一个有名字的中间产物、且这个产物之后被**另一个**代码单元读走」，
   就是一处候选边界。有名字 = 变量名、文件名、消息体、事件名，MUST 是源码里真实出现的标识符。
2. **逐个过四条规则**：对每处候选边界，按上表规则 1–4 判它成不成节点。
3. **平手时拆，不合**：拆与不合都说得通、四条规则都判不下来时，**MUST 拆**。
   理由是规则 4 已经定了方向——"拆到再拆下去就没有独立输入输出为止"；
   平手意味着还没拆到那个头。**MUST NOT 因为"合起来更好看"或"合起来图更清爽"而合**。
4. **记下被合并的候选**：任何一处候选边界最终没成节点，MUST 在那个节点的 `responsibility` 里
   写清它把哪几步合进来了。这样两次抽取即使切法不同，也能对着 `responsibility` 看出分歧在哪。

5. **把这一遍的账留下**：交出描述时 MUST 一并说清 **枚举出多少处候选边界、其中多少处成了节点、
   合并掉的是哪几处、各自依据哪条规则合并**。没有这份账，"我按规则切的"就无法复核——
   实测两次抽取切出 16 个和 11 个节点，都自称按规则做的，差别全在没留账的那几处合并上。

> **自检**：把同一个模块隔一段时间再抽一次，节点集 MUST 相同。不同就是这一节的枚举顺序没被遵守，
> 或者某处候选边界的判定有歧义——MUST 回来把那一处写清楚，MUST NOT 两张图各说各话。
>
> **最常见的违规是"该拆没拆"**：把一串顺序步骤合成一个大节点，看起来图更清爽，
> 但每一步的产物其实都被下一步单独读走了。判据只认**有没有有名字的中间产物被另一个代码单元读走**，
> **不认"合起来更好看"**。典型例子：向云服务「提交任务 → 轮询进度 → 下载结果」三步，
> 三个产物（提交凭据、解析结果、下载产物）各自被下一步读走，**MUST 切成三个节点**，
> MUST NOT 并成一个"云端处理"。

**MUST NOT 因为某个环节"看起来重要"就把它从内联提升成独立节点**——判据只有"有没有独立的输入输出、上下游能不能指向它"这一条。

## 常见的判错

| 会怎么错 | 正确做法 |
|---|---|
| 把同一个 Agent 的重试轮画成两个节点 | 重试不是新节点（规则 2）；怎么画见〈同会话追轮怎么画〉 |
| 为了表达重试而画一条从自己到自己的边 | **契约不允许自环**（校验规则 R-18 会直接报错）。见〈同会话追轮怎么画〉 |
| 把并发派出的 N 份同一个子代理画成 N 个节点 | **一个节点**，份数由该节点的 `concurrency` 表达 |
| 把日志上报、埋点、进度广播画成节点 | 不算（规则 3） |
| 把一个大函数里的每个 `if` 都画成岔路口 | 外部指认不出来就不算（规则 1） |
| 把一个 Agent 的"取证阶段"和"下结论阶段"拆成两个节点 | 同一次会话、外部只看到一进一出 → **一个节点** |
| 把同一个主会话的不同**阶段**（先澄清、再设计、再实现）各画成一个 Agent 节点 | 同一套系统提示词 → **一个 Agent 节点**；阶段之间的推进是这个节点上的边或它的职责描述 |
| 项目把发起会话抽成了一个统一执行器，就顺着那一处数出「1 个 Agent」 | 执行器是运输工具不是执行者，见〈到底看哪一段来分 Agent〉 |
| 首轮用户消息里的开场白不一样（"你是编码助手" / "你是建单助手"），就当成不同的 Agent | **那是参数不是本体**——系统提示词没变就是同一个 Agent。开场白差异写进它的 `responsibility` |
| 同一件事能换不同 provider 跑（Claude / Codex / cursor…），就按 provider 各画一个 | **换 provider 是换参数**，同一个节点；provider 清单写进 `responsibility` 或 `concurrency.note` |
| 给一个 Agent 准备输入的那段程序，这次切成节点、下次并进去 | 它产出的东西（提示词文件、首轮消息、入参 JSON）被 Agent 单独读走 → **是独立节点**，两次都要切 |

## 到底看哪一段来分 Agent

**只有系统提示词变了，才是另一个 Agent。** 其余的变化都是**同一个本体的不同参数**：

| 变的是什么 | 算几个 Agent |
|---|---|
| **系统提示词换了一套**（换了 preamble / instructions / system 消息的正文） | **另算一个** |
| **走的是另一套客户端、另一条调用链**，且那条链有自己的系统提示词常量 | **另算一个** |
| 换 provider / 换模型 / 换温度 / 换工具选择策略 | **同一个**，参数不同而已 |
| **首轮用户消息不一样**（按任务类型换开场白、换任务描述） | **同一个**，系统提示词没变 |
| 同一套系统提示词里按条件**追加或替换其中一段** | **同一个**，条件写进入边的 `trigger` |
| 重试、并发多份、同会话追一轮 | **同一个**（规则 2） |

> **怎么落地**：找到真正传给模型当系统提示词的那个东西——它可能叫 `system` / `preamble` /
> `instructions` / `SystemPrompt`，也可能是一份被写进工作目录、由 CLI 自己读走的 brief 文件。
> **顺着它数**。若这份东西对所有任务类型都相同，那就是**一个** Agent 节点，
> 任务类型的差异写进它的 `responsibility`。

**MUST NOT 数到「会话执行器」**：成熟项目常把"发起模型会话"抽成一个统一执行器
（`runAgent()` / `Client.Chat()` / 一个 `agent.go`）。执行器是**运输工具**，不是执行者——
但要注意，**执行器统一不等于 Agent 只有一个**：若上层有几处各自装配了不同系统提示词的调用，
那就是几个 Agent。**看系统提示词，不看执行器。**

**判不准时 MUST 两个数都给出来**：按这条判据数是几个、按别的口径数是几个，差在哪几处，
写进描述的范围边界交使用者判，MUST NOT 自己挑一个数悄悄定了。

### 一个真实例子

一个多 Agent 编排平台：后端把十几种 CLI agent 包在统一接口后面调度；
任务按类型分成"处理 issue / 快速建单 / 聊天"三种，各有各的开场白。

**它是 3 个 Agent 节点，不是 3 种任务类型那个 3，也不是十几种 provider 那个十几**：

- 三种任务类型的开场白走的是 `Execute(ctx, prompt, opts)` 的 `prompt` 入参，
  即**首轮用户消息**；真正的系统提示词是一份被写进工作目录、由 CLI 自己读走的 runtime brief，
  **对所有任务类型都相同** → 这一堆合起来是**一个**节点。
- 十几种 provider 是**同一个节点的参数**，不是十几个节点。
- 另有两处各自带**自己的系统提示词常量**、走**自己的客户端**：一处生成后续动作建议，
  一处给会话起标题 → 这是**第二、第三个**节点。

> **这个例子最初被写错过，错法很典型，所以留在这里当反面教材。**
> 初版写的是"2 个"——漏掉了起标题那一处。漏因不是判据用错了，而是
> **没有把全仓的装配点数完就下了结论**：主链路上的那个太显眼，顺着它一路读下去，
> 读完就以为读全了。旁边那两处又小又不在主干上，各自只有几十行。
>
> **所以〈切法 MUST 可复现〉第 2 步的"全仓搜一遍装配点"MUST 真的搜一遍全仓**，
> 而不是"顺着主链路读到哪算哪"。检索词至少覆盖：拼 system / preamble / instructions 的地方、
> 建 agent 对象的地方、发起 completion 或起 CLI 子进程跑一次会话的地方，
> 以及**独立于主链路的那些小服务**（起标题、出摘要、生成建议、分类打标——
> 这类"顺手让模型干一下"的调用最容易被整片漏掉）。
> 搜完 MUST 把命中清单逐条对照已抽出的 Agent，对不上的就是漏网的。

### 几个 Agent 的系统提示词共用了一段公共 brief

**先分清是哪种情况**，两种的处理完全不同：

| 情况 | 怎么算 |
|---|---|
| **系统提示词完全相同**，只有首轮用户消息按任务类型不同 | **一个 Agent 节点**。任务类型差异写进 `responsibility`，MUST NOT 拆成几个 |
| **每个 Agent 各有自己的系统提示词，但都以同一段公共 brief 打头**（brief + 各自那段） | **各算一个 Agent 节点**，因为系统提示词全文不同 |

第二种情况下，共用关系 **MUST 在提示词字段上如实体现**：

- 每个节点的 `system_prompt` **MUST 指向那段公共 brief 的同一个来源**（同一个 `file` 与同一段 `from`/`to`）。
  这样使用者点开任意两个 Agent，看到同一份来源，**一眼就知道它们打头那段是共用的**。
- **区分它们的那一段 MUST 落在各自的 `source.refs` 与 `responsibility` 里**——
  refs 指到各自的构建位置，responsibility 用一句话说清这一个扮演的是谁。

**MUST NOT 给它们编造各不相同的提示词来源**去制造"看起来不共用"的假象。

> 分不清是哪种情况时（例如读不出那段公共 brief 到底是被当系统提示词还是被拼进用户消息），
> MUST 两个数都给出来，差在哪几处写进描述的范围边界交使用者判，
> MUST NOT 自己挑一个数悄悄定了。

## 同会话追轮怎么画

复用同一个会话追加一轮**不算新节点**（规则 2）。但"不算新节点"不等于"画成一条自己到自己的边"——
**契约不允许自环**：`from` 与 `to` 相同时校验规则 R-18 直接报错。所以按下面两种情形分开处理：

| 情形 | 怎么画 |
|---|---|
| **追轮由别的节点发起**（另一个节点拿着已有的会话 id 再发一次消息） | 画成**那个节点 → 这个 Agent** 的一条边，追轮传的东西作为该边的一个传递物。与同方向的其它边按同向合并规则合成一条 |
| **追轮发生在 Agent 自己的循环里**，没有外部节点发起（自己的 hook 判定"没调工具"就自己补一轮） | **不画边**。MUST 写进这个 Agent 的 `responsibility`，并在 `stop` 里说清这一轮算不算步数 |

**MUST NOT 为了表达追轮而伪造一条自环边**，也 MUST NOT 硬拆出一个假节点当发起方去绕开自环限制。
读不出是哪种情形时按第二种处理，并在 `field_confidence` 里把相关字段标 `inferred`。

## 事实基准

本约定的事实基准是一次对真实模块的完整抽取：一个内控审计编排被切成 **10 个节点**（8 个程序 + 2 个 Agent）与 **15 条单向边**（按「同向合并」规则合并后 14 条）。

那次抽取里做过的几个判断，可以直接当样例对照：

- 「材料清册与指纹」「台账复用查找」「材料分组与规划提示词构建」是三个节点，因为每一步的产物都被下一步单独取用，上下游指得到。
- 「补交提醒」是调度节点对判定 Agent **复用同一会话追加一轮**——按规则 2，**不是新节点**，是 `调度 → 判定` 那条边上的一个传递物。
- 「取消信号」同样落在 `调度 → 判定` 那条边上；它与「补交提醒」同方向，按同向合并规则**合成一条边、两个传递物**。
- 索引段、梳理段、回执落盘、取材路径审计、观测型旁路、embed 注入链这几类支线**没有上图**——观测型旁路按规则 3 不算节点，其余是当次抽取主动划定的范围边界，**这类主动排除 MUST 在描述里写清楚**（见 `抽取纪律.md` §范围边界）。

## 粒度定完之后

节点数就可复核了：同一个人、同一份判据、两次抽取 MUST 得到同一个数。得不到就是判据有歧义，MUST 回来把判据写清楚，MUST NOT 让两张图各说各话。
