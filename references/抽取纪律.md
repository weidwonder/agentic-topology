# 抽取纪律

> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> **本文是自足的**：不引用任何其他技能或外部文档。
> 字段怎么填见 `编排描述格式.md`；什么算一个节点见 `节点粒度约定.md`。

## 0. 这份纪律要挡住的那件事

这张图最大的风险不是画错，是**画漏**——漏掉的 agent 和调用边在图上根本不会出现，看图的人不会有任何察觉，然后照着一张缺东西的图去改系统。

所以下面每一条都指向同一个目的：**让"我没查到"和"它没有"永远分得开**。

## 1. 真相方向铁律

> **源码是唯一真相源。项目文档只作弱参考。**

- 每条事实的 `source.refs` MUST 指向**源码位置**（`文件:行` 或 `文件:起-止`）。
- 仅有文档来源、未经源码核实的条目 **MAY 保留，但 MUST 标 `doc_only: true` 且 `confidence` MUST 是 `inferred`**，并进核对清单。**MUST NOT 标 `certain`。**
- 文档与源码冲突时**一律以源码为准**，并在该条目的 `source.conflict_note` 里记下采信了哪边。

**为什么**：后续的设计文档与缺陷修复都会改动代码与特性，**文档滞后是常态**。真实抽取里就撞见过：设计文档写的是一个月前的状态，提示词版本文档写 v1 实际 v2/v9、重试上限文档写 2 源码是 3、文档说规划输入含指纹而源码已改成不含。照着文档画，画出来的是一张过期的图。

## 2. 三步流程

### 第 1 步：概览目标项目的文档架构

看清楚这个项目有哪些文档、放在哪、大致讲什么。**只是建立导航感，不是采信它们。**

### 第 2 步：向使用者问一次

> "除了源码，有没有可直接参考的、准确表示项目情况的需求与代码架构文档？"

- 使用者指认的文档登记为**导航与理解辅助**——用来快速定位该读哪些源码文件，**不作为任何一条事实的来源**。
- **使用者不作答时降级为自行概览，MUST NOT 阻塞。** 这是整个流程唯一的人工输入点，它是个加速器，不是前置条件。
- **只问这一次。** MUST NOT 在抽取过程中反复回来问。

### 第 3 步：读源码抽取实体并核实

**所有** agent 节点、程序节点、判断节点、工具、MCP、Skill、子代理、边 **MUST 来自读源码**。

推荐的收窄顺序（这是效率建议，不是硬性次序）：

1. 从**入口**出发——用户操作、命令行、定时任务、消息消费者，找到这套编排是被什么点着的。
2. 顺着入口往下追调用，把**会话调用点**找出来——每一处装配了系统提示词的地方就是一个 Agent 节点的候选。
3. 对每个 Agent，读它的**装配点**（工具清单、MCP 注册、Skill 列表、上限设置在哪几行），而不是读它的提示词正文来猜。
4. 把 Agent 之间的**程序段**按 `节点粒度约定.md` 切成节点。
5. 顺着主干把**边**补齐：每两个相邻节点之间到底传了什么、靠什么传、什么条件下传。
6. **再专门找一遍「不顺着主干走」的边**——这一步 MUST 单独做一遍，MUST NOT 混在第 5 步里顺手带过。
   主干边（A 干完交给 B）是顺着读代码就会撞上的；下面这三类不会，漏的几乎都是它们：

   | 类型 | 长什么样 | 到哪里找 |
   |---|---|---|
   | **失败回灌边** | 校验／闸门不通过，把结构化的错误原因塞进**下一轮**的输入或提示词，让上游重做 | 重试循环里那个跨轮次持有的变量（`lastErrors` / `rejectionErrors` 这类）：先看它在哪被**赋值**，再看它在哪被**读走**——读走的那一端就是这条边的终点 |
   | **带外信号边** | 不走正常返回值，由旁路直接打断或追加一轮：取消、超时熔断、看门狗、补交提醒 | `cancel*` / `abort*` / `kill*` / 看门狗回调 / 复用同一会话 id 再发一次消息的地方 |
   | **同会话追轮边** | 复用**同一个会话**再追一轮，不新开会话 | 传了已有 `conversationId` / `sessionId` / `threadId` 的调用点。**由别的节点发起才画边；发生在 Agent 自己循环里的不画边**——契约不允许自环，处理办法见 `节点粒度约定.md` 〈同会话追轮怎么画〉 |

   **同一遍里还 MUST 找一类节点：条件性执行者。**

   > **这一项问的是「有没有别的 Agent」，不是「已知的 Agent 在什么条件下跑」。**
   > 答"某某 Agent 要开关打开才派发" **不算做过这一项**——那是已知 Agent 的触发条件，
   > 本来就该写进它入边的 `trigger`。这一项要找的是**主干上根本没出现过的、另一套 Agent**。
   > 做法：全仓搜一遍**拼装提示词的地方**（拼 system prompt / preamble / instructions
   > 的函数，尤其是按任务类型分发到不同构建函数的那个分发点），把搜到的每一处**逐个**
   > 对照已抽出的 Agent 清单；对不上的那些就是漏网的。
   > 诊断按钮、连通性自检、降级兜底、一次性探针都在此列。
   >
   > **只搜「发起模型调用」的地方是不够的**——成熟项目往往只有一处统一执行器，
   > 顺着它数会数出 1 个 Agent。也 **MUST NOT 只认 `SystemPrompt` 这类字段名**：
   > 有的项目把通用 brief 放那个字段，真正区分角色的指令走首轮任务消息。
   > 判据见 `节点粒度约定.md` 〈到底看哪一段来分 Agent〉；**判不准时两个数都给出来**，
   > 把分歧交给使用者判，MUST NOT 自己挑一个悄悄定了。

   MUST 上图，条件写进它入边的 `trigger`。到哪里找：写着"某某情况下**增派**一个""仅当…才跑"
   "这一类项目额外加一个"的地方；以及**装配了另一套系统提示词**的分支
   （换了提示词文件、换了角色说明、加载了另一份指令，都算另一个执行者）。
   **MUST NOT 因为"它不总是跑"就不画**——不总是跑的执行者仍然是执行者。

   **判据（MUST 按这条判，MUST NOT 凭直觉）**：一个上限或一个信号，只有在它**纯粹让当前节点自己停下**时，
   才只记进该节点的 `stop`；只要它**把控制权或数据交回给另一个节点**（哪怕只是让上游带着新输入重来一次），
   它 MUST 同时是一条边。**只记进 `stop` 就漏了一条边**——这是实测最高发的漏项。

## 3. 允许与禁止

**允许**：读目标项目的文件；向使用者提问一次可参考文档；写出描述文件与 HTML。

**禁止（每条都是 MUST NOT）**：

1. **MUST NOT 修改目标项目任何文件。** 全程只读。不新建、不改写、不删除、不格式化、不跑任何会写盘的命令。
2. **MUST NOT 把 `inferred` 或 `unread` 呈现为 `certain`。**
3. **MUST NOT 编造**项目里不存在的节点、工具、MCP、Skill、子代理或边。
4. **MUST NOT 给出架构好坏的判断。** 描述与图里不出现任何评价性措辞——不写"这里设计得不好""缺少重试机制是个隐患""建议加上限"。这张图的用途是**让人看清楚到能自己下判断**，工具本身不给任何评价。
5. **MUST NOT 把项目文档当作某条事实的唯一来源**（见 §1）。
6. **MUST NOT 把目标项目内容发送至任何外部服务。**
7. **MUST NOT 为了让校验通过而编造字段值。** 见 §5。

## 4. 读不出来的时候

**MUST 明说没读懂哪部分**，把对应节点或字段标成 `unread`，让它进核对清单。

- **MUST NOT 产出空图。**
- **MUST NOT 猜测结构**去把图填满。
- 整体读不出来时，明说卡在哪，并提示使用者改用手写描述那条路。

三种典型的"读到了但读不出来"，都属于 `unread`：

| 情形 | 例子 |
|---|---|
| 决定权不在本仓 | 某个上限的语义在内嵌的运行时里，本仓源码看不到它到底限的是什么 |
| 动态派发 | 配置化路由、反射调用——代码在这儿，但走哪条分支由运行期数据决定 |
| 范围之外 | 调用链穿到了本次抽取范围之外的模块 |

## 5. 自查与 re-ask 上限

写完描述 MUST 自己跑一次校验：

```bash
node scripts/validate.mjs <描述文件>
```

不通过就照问题清单改。**MUST 最多修正 3 轮**；3 轮仍不通过 MUST 停下来，把问题清单原样交给使用者。

> **MUST NOT 无限重试，更 MUST NOT 为了让校验通过而编造字段值。**
> 一个"校验通过但内容是编的"描述，比不出图坏得多——不出图至少诚实，编出来的图会被人当真。
> 填不出某一项时正确的做法是：把你**真的读到的**写上去，把可信度标成 `unread`，让它进核对清单。

## 6. 范围边界要写清楚

一个真实子模块的节点边数很容易超出单屏。**MUST NOT 为了让图好看就静默裁掉节点或边**——过密靠分堆折叠和筛选解决。

确实需要划定范围（只画某个子模块、主动排除某几条支线）时：

- MUST 在 `graph.entry` 或对应节点的 `responsibility` 里**写清楚这次画的是哪一段**。
- 主动排除的支线 MUST 逐条写进描述——把它们记进最靠近的那个节点的 `outputs`，或作为一条 `confidence: unread` 的说明性条目进核对清单。
- **MUST NOT 让"没画"和"没有"看起来一样。**

## 6bis. 目标大到一个上下文装不下时：MUST 分批落盘

**判据（满足任一即按本节做）**：圈定范围超过 **1 万行源码**，或超过 **20 个文件**，
或读到一半发现"要同时记住的东西已经比能记住的多"。

一次性读完再动笔，会在读到后面时把前面读过的挤出去。**症状是静默的**：
产出的描述看不出哪些结论是在记忆已经模糊之后写下的，`confidence` 照样标着 `certain`。
**这比读不出来更危险**——读不出来至少会标 `unread`。

**`analysis_complete` MUST 先写 `false`，最后才改 `true`。**

这一条是机制防线，不靠自觉：**建这个文件的第一笔就 MUST 写 `analysis_complete: false`**，
只有在**全部批次读完、自查清单逐条过完之后**，才把它改成 `true`。

理由是实测出来的：一次分析被外部限流硬切断，模型没有机会执行任何收尾动作，
留下的描述里 `analysis_complete: true`、35 条 `certain`、0 条 `unread`，
**范围边界里一个字都没提它没跑完**——因为那个 `true` 是它在"还以为自己会继续写"的时候写下的。
只看这份文件，得到的是一张看起来完整、可信度很高、却漏掉三分之一 Agent 的图。

**先写 `false` 就没有这个问题**：任何非正常结束留下的都是一份诚实标着"没分析完"的描述，
出图时页面顶部会常驻"还没分析完，这张图不全"的告示。
**MUST NOT 为了"看起来干净"提前把它置成 `true`。**

**MUST 这样做**：

1. **先分批**：按子系统或调用链把范围切成几批，每批控制在能一次读完的量。
   切法与批次清单 MUST 写进描述的范围边界，让人能看出你是分几批读的。
2. **每读完一批就落盘**：把这一批抽出的节点与边**当场写进** `.topology.yaml`，
   `analysis_complete` 置 `false`。**MUST NOT 攒着等全部读完再一起写。**
3. **下一批接着补**：从文件里已有的内容接着写，**MUST NOT 从头重来**（§7 与文末〈断点文件就是描述文件本身〉）。
4. **全部批次完成后**才把 `analysis_complete` 置 `true`。

**如果中途还是发生了上下文压缩或截断**：
MUST 在描述的范围边界里**明写这件事**（哪一批之后发生的），
并把该批次里**没有当场落盘**的结论按 §4 降档处理——
`certain` 降到 `inferred`，因为它们是在记忆已经不完整时写下的。
**MUST NOT 假装没发生过。**

## 7. 中断与二次生成

- **中断后继续**：已读出的部分保留在描述文件里，`analysis_complete` 置 `false`，下次从描述里已有的节点接着补。**MUST NOT 从头重来。**
- **二次生成**：对同一项目再跑一次时 **MUST NOT 覆盖**已有的描述，另存一份并告诉使用者已有一份，由使用者决定用哪份。
- **过期提示**：描述里的 `generated_at` 与 `source_project` 就是判断依据。出图时若能判断已过期则提示，**MUST NOT 自动重跑**。

## 8. 收尾自查清单

交出描述之前逐条过：

- [ ] 每个 Agent 的工具、MCP、Skill 三份清单**分开填**了，一个都没有的写了 `[]`
- [ ] 每个节点都填了 `concurrency`，只跑一个的写了 `1`
- [ ] `stop.limits` 四个键都在，`not_set` 与 `unread` 没混用
- [ ] 每条 `source.refs` 都指向源码位置，只有文档来源的都标了 `doc_only: true` + `inferred`
- [ ] 标了会派子代理的 Agent，子代理都是图上的一等节点，回传边都写了 `screening`
- [ ] 没有双向边；同一对节点同一方向只有一条边
- [ ] **第 3 步第 6 项那一遍单独做过了**：失败回灌边、带外信号边、同会话追轮边、
      条件性执行者各找过一遍，找不到也 MUST 是"找过之后确认没有"，MUST NOT 是"没想起来找"
- [ ] 所有"增派""仅当…才""这类项目额外加一个"的分支都过了一遍，
      其中**装配了另一套系统提示词**的都成了独立节点
- [ ] `analysis_complete` 是**建文件时写 `false`、此刻自查完才改 `true`** 的，
      不是一开始就写 `true`（§6bis）
- [ ] 圈定范围超过 1 万行或 20 个文件时，**是分批读、每批当场落盘**的（§6bis），
      批次清单写进了范围边界；中途若发生过上下文压缩，已明写并把未落盘的结论降过档
- [ ] **候选边界的账留下了**：枚举出多少处、多少处成了节点、合并掉哪几处、依据哪条规则，
      都写清楚了（见 `节点粒度约定.md` 〈切法 MUST 可复现〉第 5 步）
- [ ] **全仓的提示词拼装处搜过一遍**，每一处都能对上已抽出的某个 Agent 节点；
      对不上的都补成了节点或写进了主动排除范围。
      **只答"某 Agent 要满足什么条件才跑"不算做过这一项**
- [ ] 项目若有**统一的会话执行器**，Agent 数是按**角色指令**数的，不是数执行器、也不是只认 `SystemPrompt` 字段得出的；
      两种数法结果不同时，两个数都写出来了并说清分歧在哪
- [ ] 每一条写进 `stop.conditions` / `stop.limits` 的上限与信号都回头过了一遍：
      纯粹让自己停下的留在 `stop`，会把控制权或数据交回给别的节点的**同时也补了一条边**
- [ ] 每条边的每个传递物都写了产生时机和传递时机，两者确实分开想过
- [ ] 描述与图里没有任何评价架构好坏的话
- [ ] 目标项目一个文件都没改过
- [ ] `node scripts/validate.mjs` 退出码是 0

## 断点文件就是描述文件本身

中断后继续时，**不另建断点文件**——已经写出来的那份 `.topology.yaml` 就是断点：

- 中断时 MUST 把 `analysis_complete` 置为 `false` 并把已读出的节点与边**原样留在文件里**。
- 续跑时 MUST 先读这份文件，把里面已有的 `nodes[].id` 与 `edges` 当作**已完成**，只补缺的部分。
  **MUST NOT 从头重来**，也 MUST NOT 覆盖已有条目的 `source` 与 `confirmed_at`。
- 全部补齐后把 `analysis_complete` 置为 `true`。
- 对同一项目重新分析（不是续跑）时 **MUST NOT 覆盖**已有的 `.topology.yaml`：
  另存为 `<原名>.2.topology.yaml` 并告诉使用者已有一份，由使用者决定用哪份。
