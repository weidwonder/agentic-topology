# 编排描述格式

> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> **本文是自足的**：填一份合格的描述只需要这一份文档，不引用任何其他技能或外部文档。
> 界面上这些字段怎么说人话，见 `界面用语表.md`；什么算一个节点，见 `节点粒度约定.md`。

## 0. 一句话

一份编排描述是**一个文件**：`<主题>.topology.yaml`（受限 YAML 子集）或 `<主题>.topology.json`（标准 JSON）。两者表达同一套契约。

**填不齐必填项就出不了图**——校验器会拒绝，并指名是哪个节点、哪条边、缺哪一项。这是有意的：一张"看着完整、其实缺东西"的图比不画更坑人。

## 1. 受限 YAML 子集：能用什么、不能用什么

`.topology.yaml` MUST 只用下列语法：

- 块映射 `key: value`（缩进 **MUST 用空格**，MUST NOT 用 Tab）
- 块序列 `- item`
- 标量：裸标量、单引号字符串、双引号字符串（双引号内支持 `\\` `\"` `\n` `\t` 三种转义）。
  **引号标量 MUST 在同一行内闭合**——长文本按习惯换行会直接报 `E_SYNTAX`，要换行请用下一条的 `|` / `|-`
- 多行块标量 `|`（保留结尾换行）与 `|-`（去掉结尾换行）
- 整行注释 `# ...`；行尾注释（**只在裸标量后生效**——引号字符串里的 `#` 不是注释）
- `true` / `false` / `null`（空值也记为 `null`）、整数
- **空序列字面量 `[]`** —— 这是唯一被允许的流式写法（YAML 里没有别的办法表达空序列，而三份清单「一个都没有」是常态）。**非空序列一律用块序列 `- item`。**

**MUST NOT 用**（用了就报 `E_SYNTAX` 并指出行号）：

| 不支持的语法 | 长什么样 |
|---|---|
| 锚点与引用 | `&anchor` / `*anchor` |
| 标签 | `!!str` |
| 流式映射 | `{a: 1}` |
| **非空**流式序列 | `[1, 2]`（空的 `[]` 是允许的，见上） |
| 多文档 | 行首 `---` |
| 折叠块标量 | `>` |
| 复杂键 | `? ` |
| Tab 缩进 | 任何位置的 `\t` |
| **跨行的引号标量** | `name: "第一行`⏎`  第二行"` —— 引号 MUST 在同一行闭合，多行文本改用 `\|` 或 `\|-` |

文件编码 MUST 是 **UTF-8 无 BOM**。

> **为什么收这么窄**：这份格式的第一读者是人。YAML 全集里那些高级语法既难写对也难读懂，还会让"我明明写了"变成"解析出来不是那个意思"。收窄之后，解析器的行为可以被完全说清，出错时能指到具体那一行。
> **写不动 YAML 的时候**：改用 `.topology.json`，字段完全一样，Node 原生解析，零风险。

## 2. 顶层结构

```yaml
schema_version: 1                              # 必填，当前只接受整数 1
source_project: "~/projects/aiudit_platform"   # 必填，被分析的项目路径或名字
generated_at: "2026-08-26"                     # 必填，YYYY-MM-DD
analysis_complete: true                        # 必填，false 时图上会标「分析未完成，此图不完整」
                                               # 自动分析时 MUST 建文件就写 false、全部读完自查过才改 true
graph:                                         # 必填，见 §3
nodes:                                         # 必填，见 §4；可以是空数组（空态）
edges:                                         # 必填，见 §6；可以是空数组
groups:                                        # 选填，见 §8
```

**闭集校验（MUST 知道）**：契约之外的键一律报 `E_UNKNOWN_FIELD` 并拒绝出图。**不是静默忽略**——静默忽略拼错的字段名，会让"我明明填了"变成"图上就是没有"。

**哪些块是闭集？下面这八个，全都是。没有"可扩展的块"这一说：**

| 闭集对象 | 允许的键 |
|---|---|
| 顶层 | `schema_version` `source_project` `generated_at` `analysis_complete` `graph` `nodes` `edges` `groups` |
| `graph` | `topology` `context_sharing` `entry` `exits` |
| `graph.exits[]` | `name` `kind` `condition` `source` |
| `nodes[]` | 见 §4（`agent` 与非 `agent` 允许的键不同） |
| `nodes[].stop` | `conditions` `limits` |
| `edges[]` | 见 §6 |
| `edges[].payloads[]` | `content` `produced_at` `delivered_at` |
| `groups[]` | `id` `name` `order` |
| `source`（节点、边、exits 各自的） | `refs` `confirmed_at` `doc_only` `conflict_note` |

> **想加一句自由说明时，MUST 用契约里已有的那几个口子，MUST NOT 自己造键。**
> 已有的口子只有三个：`concurrency.note`、`source.conflict_note`、以及各处的
> `responsibility` / `purpose` 正文。
> 比如"翻遍全仓也没找到成本上限"这句话，**没有** `stop.note` 可以放——
> 它的去处是 `stop.limits.cost` 那一格本身（写 `not_set` 并在 `conflict_note` 里说明为什么）。
> 造一个新键出来只会被 `E_UNKNOWN_FIELD` 拦下，而且拦得对：多一个键就多一处只有你知道的约定。

## 3. `graph`：整图层

| 键 | 必填 | 取值 |
|---|---|---|
| `topology` | 是 | `peer_loop` / `manager_worker` / `decentralized_handoff` / `fixed_workflow` |
| `context_sharing` | 是 | `full` / `isolated` / `mixed` |
| `entry` | 是 | 自由描述：谁触发、在什么条件下进入 |
| `exits` | 是 | 数组，至少一项 |

> **整张图只有一个 Agent 节点时怎么填**：这一格问的是**谁看得见谁的上下文**。
> 只有一个 Agent 节点时，参与方就是**它自己被跑起来的那几次**——
> 这个问题照样成立，MUST NOT 因为"只有一个"就随手挑一档填。
>
> | 情况 | 填 |
> |---|---|
> | 每次都是全新会话，上一次的上下文不带过来 | `isolated` |
> | 会续上上一次的会话（resume / 复用 session） | `full` |
> | 有的路径续、有的不续 | `mixed`，并在 `graph.entry` 里写清哪条是哪种 |
>
> 判据 MUST 落在源码上：**找到那个决定"要不要把上一次的会话 ID 传下去"的地方**，
> 看它在哪些路径上传、哪些路径上清空。

**`topology` 与 `context_sharing` 是两件正交的事，MUST 分开判**：共享上下文的编排也可以是中心化调度的，隔离的 Agent 也可以被集中派活。把两者绑在一起想会漏掉很多合理组合。

`exits[]` 每项：

| 键 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 这个终点叫什么 |
| `kind` | 是 | `normal` / `abnormal` / `cancelled` |
| `condition` | 是 | 什么条件下走到这个终点 |
| `source` | 是 | 见 §5 |

**MUST 把异常终点也列全**——只列"成功"那一条，等于把这套编排会怎么失败藏起来了。

## 4. `nodes[]`：节点层

### 4.1 三类通用（`agent` / `program` / `decision` 都要填）

| 键 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 图内唯一，匹配 `^[A-Za-z0-9_.-]{1,64}$` |
| `name` | 是 | 这个节点叫什么 |
| `kind` | 是 | `agent` / `program` / `decision` |
| `responsibility` | 是 | 一句话说清它干什么。**这句会直接印在图上的方块里**，所以要写成人能一眼读懂的话 |
| `inputs` | 是 | 收什么 |
| `outputs` | 是 | 交出什么 |
| `concurrency` | 是 | 见下。**三类都要填**，只跑一个也 MUST 显式写 `default: 1` |
| `confidence` | 是 | `certain` / `inferred` / `unread`，见 §7 |
| `source` | 是 | 见 §5 |
| `group` | 否 | 分组 ID。不填时详情里显示「未填写」。**整行省掉、写 `group:`（留空）、写 `group: null` 三者等价**，都算没填；只有写了一个 `groups[]` 里不存在的 ID 才会被拦 |
| `field_confidence` | 否 | 见 §7.2 |

```yaml
concurrency:
  default: 3          # 必填，≥1 的整数
  max: 4              # 选填，有上限时写上限值；不填表示与 default 相同
  note: "由上游的排队分发控制"   # 选填
```

**并发数为什么是必填**：它最影响一套编排跑起来是什么样。**MUST NOT 取 `not_set`**——一律显式写值，只跑一个就写 `1`。

### 4.2 `kind: agent` 专属

| 键 | 必填 | 说明 |
|---|---|---|
| `system_prompt` | 是 | 二选一形态，见下 |
| `tools` | 是 | 字符串数组。一个都没有写 `[]` |
| `mcp` | 是 | 字符串数组。一个都没有写 `[]` |
| `skills` | 是 | 字符串数组。一个都没有写 `[]` |
| `stop` | 是 | 见下 |
| `spawns_subagents` | 是 | `true` / `false` |
| `subagents` | `spawns_subagents: true` 时必填 | 见下 |

**这三份清单 MUST 分列，MUST NOT 合并成一份「工具」**。合并之后就看不出"它能搜资料，但那是外挂来的，而且被白名单裁过"这种事——而这恰恰是判断一个 Agent 能干什么的关键。

`system_prompt` **MUST 恰好命中一种形态**（两种都给或都不给报 `E_PROMPT_FORM`）：

```yaml
# 形态一：内联全文
system_prompt:
  inline: |
    你是内控审计判定师。
    只就分给你的这几项给结论，不许扩大范围。
```

```yaml
# 形态二（默认形态，推荐）：指向文件的行区间
system_prompt:
  file: "assets/prompts/internal-control-judge.v9.md"   # 相对路径以本描述文件所在目录为基准
  from: 1        # 起始行，1 起算，含
  to: 192        # 结束行，含。MUST ≥ from
```

> **默认用形态二**：这样让 AI 读出一份描述时，不需要先把提示词整篇读一遍，省事也省钱。真要看的时候，出图会按行号把那一段取回来展开。

> **几个 Agent 的系统提示词都以同一段公共 brief 打头时，它们的 `system_prompt` MUST 指向那段 brief 的同一个来源**（同一个 `file`、同一段 `from`/`to`）：使用者点开任意两个 Agent 看到同一份来源，就知道打头那段是共用的。区分它们的那一段写进各自的 `source.refs` 与 `responsibility`。MUST NOT 编造各不相同的来源制造"看起来不共用"的假象。
>
> **注意先分清**：若系统提示词**完全相同**、只是首轮用户消息按任务类型不同，那是**一个** Agent 节点，MUST NOT 拆成几个（判据见 `节点粒度约定.md`）。

```yaml
stop:
  conditions:                     # 必填，至少一条：什么情况停
    - "取证步数撞 400 次工具调用，当场取消会话"
    - "同一轮被闸门退回 4 次即熔断"
  limits:                         # 必填，四个键 MUST 全部出现
    steps: "400 次工具调用/attempt"
    time: "15 分钟无进展被外层中止"
    cost: not_set                 # 见 §7.1：已读到那个位置、确认确实没设
    consecutive_failures: "同 attempt 内被退回 4 次"
```

```yaml
subagents:
  - node: "SUB1"                  # 必填，MUST 指向 nodes 里真实存在的一个节点
    note: "负责单份材料的引文定位"  # 选填，用于父级详情里的子卡摘要
```

**子代理是图上的一等节点**：它自己有完整的节点记录，父 → 子是一条正常的边。父级详情里那张子卡只是**快捷视图**，MUST NOT 成为子代理信息的唯一入口，也 MUST NOT 因为做了子卡就把子代理从图上撤掉。

### 4.3 `kind: program` 与 `kind: decision` 专属

| 键 | 必填 | 说明 |
|---|---|---|
| `purpose` | 是 | 起什么作用：它夹在 agent 之间是为了解决什么问题。`decision` 还 MUST 写清**它按什么分岔** |

**MUST NOT 交叉填**：`agent` 节点写 `purpose`，或 `program` / `decision` 节点写 `system_prompt` / `tools` / `mcp` / `skills` / `stop` / `spawns_subagents` / `subagents`，都会报 `E_UNKNOWN_FIELD`。

## 5. `source`：来源与确认时间

节点、边、`exits[]` 各自必填。

```yaml
source:
  refs:                                        # 必填，至少一条
    - "src/main/internal-control/workflow.ts:920-988"
  confirmed_at: "2026-08-26"                   # 必填，YYYY-MM-DD
  doc_only: false                              # 选填，缺失视为 false
  conflict_note: "spec 写重试上限 2，源码是 3，采信源码"   # 选填
```

每条 `refs` MUST 匹配 `文件路径:行` 或 `文件路径:起-止`。

**`doc_only: true` 的条目，`confidence` MUST NOT 是 `certain`**（校验器会拦）。理由见 `抽取纪律.md` §真相方向铁律。

## 6. `edges[]`：边层

| 键 | 必填 | 说明 |
|---|---|---|
| `from` / `to` | 是 | 节点 `id`。MUST 都存在；`from === to` 报 `E_SELF_LOOP` |
| `category` | 是 | `normal` / `pass_or_skip` / `reject_or_halt`。呈现层据此取色 |
| `trigger` | 是 | 什么情况下走这条边 |
| `carrier` | 是 | `file` / `bundle` / `prompt` / `event` / `other`。取 `other` 时 MUST 另填 `carrier_note` |
| `carrier_note` | `carrier: other` 时必填 | 那是什么载体 |
| `payloads` | 是 | 数组，至少一项。见 §6.2 |
| `concurrency_control` | 是 | 同一条边被同时触发多次、或多个上游同时交东西过来时按什么规则处理。**非闭集**，常见取值：排队 / 取最新 / 拒绝 / 合并 / 不会发生 |
| `screening` | 父 → 子代理的**反向边**必填，其余选填 | 下游收下之前先查什么、什么情况下退回 |
| `confidence` | 是 | 见 §7 |
| `source` | 是 | 见 §5 |
| `field_confidence` | 否 | 见 §7.2 |

**`screening` 为什么在父子回传边上是硬性的**：子代理产出被父级采纳前有没有把关，是多 Agent 编排里最关键也最容易看不见的一件事。只画出"有个子代理"而看不到它的话被信到什么程度，等于没画。

### 6.1 边的四条规则

1. **边 MUST 单向。** 双向关系 MUST 拆成两条独立的单向边。描述里出现 `bidirectional` / `reverse` / `both_ways` 任一键即报 `E_BIDIRECTIONAL`。
2. **同一对节点、同一方向最多一条边。** 同向的多种情形 MUST 合并成一条，用**多个传递物**表达差异，而不是画多条线。违反报 `E_DUPLICATE_EDGE`。
3. 因此同一对节点之间最多两条线（一来一回）。
   **同步调用的返回 MUST 画成回来那一条边，MUST NOT 省略。**
   "A 调用 B、B 把结果交回 A" 是**两次传递**：去的时候交出去的是入参，
   回来交出去的是结果——两边的传递物不一样，产生时机和传递时机也不一样。
   省掉回来那条，图上就看不出 B 到底交出了什么、什么条件下交不出来（失败、超时、被拒）。
   回来那条边的 `trigger` MUST 写清什么情况下会回传，`payloads` MUST 写清回传的是什么。
4. **同一个子代理被并发派出多份时仍然只画一条边**，份数由该子代理节点的 `concurrency` 表达。画成 N 条平行边会撞上第 2 条被拒绝出图。

### 6.2 `payloads[]`：一条边可以带好几样东西

```yaml
payloads:
  - content: "这件活儿的说明文件"          # 必填，开放取值，据实描述，MUST NOT 往预设清单里套
    produced_at: "写好每件活儿的交代时"     # 必填，这个东西在哪一步被造出来
    delivered_at: "派活儿的那一轮"          # 必填，它在哪一步被交出去（常与产生时机不同）
  - content: "一次性的交结论凭据"
    produced_at: "调度分配工作项时"
    delivered_at: "同一轮首条消息里"
```

**产生时机与传递时机 MUST 分开填**——它们经常不是同一步，而"东西早就造好了、到很后面才交出去"正是编排里最容易出错的地方。

## 7. 可信度：这条事实有多可靠

### 7.1 三档 + 一个容易混的取值

| 取值 | 什么时候用 | 处置 |
|---|---|---|
| `certain` | 有明确源码依据 | 正常呈现，**不进核对清单** |
| `inferred` | 只有启发式线索，或只有文档来源没在代码里坐实 | 虚线呈现 + **进核对清单** |
| `unread` | 诚实读不出来：读不到，或读到了但语义在本仓看不到 | 虚线呈现 + **进核对清单** |

**`not_set` 和 `unread` 是两回事，MUST NOT 混用**——这是全表最容易填错的一对，两者处置完全相反：

- **`not_set`**（只能出现在 `stop.limits` 的四个键上）= 你已经读到那个位置、确认目标项目**确实没有设置**。它是一个**事实取值**，与 `confidence: certain` 并存；图上中性呈现，**不进核对清单**。
- **`unread`** = 你**没能读出来**。它是一个**可信度档位**，MUST 进核对清单。这时 `stop.limits` 那个键**照样写你读到的字面量**（比如 `"maxTurns=80，但它限的是什么本仓看不到"`），另在 `field_confidence` 里把该字段标成 `unread`。
- **两者分不清时 MUST 取 `unread`**，MUST NOT 默认写 `not_set`。把"我没查到"说成"它没设"，正是这张图最不该犯的错。
- **`certain` 与 `inferred` 分不清时 MUST 取 `inferred`**——保守的那一档。
- **`concurrency` 的任何字段 MUST NOT 取 `not_set`。**

> **「没设」在图上 MUST 是中性的**：跟已填的值同色同权重，不加警示色、不加告警图标、不排序置顶、不进核对清单。"没设上限好不好"是别人的判断题，不是这张图的——**这张图只陈述事实，不下判断。**

### 7.2 `field_confidence`：整体查实了，但个别字段没读出来

```yaml
field_confidence:
  stop.limits.steps: unread      # 键是本对象内已存在的字段名，点号可下探
  concurrency.max: inferred
```

- 值 MUST 是 `inferred` 或 `unread`（`certain` 是默认，不用标，标了报 `E_ENUM`）。
- 键指向不存在的字段报 `E_UNKNOWN_FIELD`。
- 这类条目 MUST 一并进核对清单，但 **MUST NOT 因此把整个节点或边降档**——整体查实了就是查实了。

## 8. `groups[]`：分组

```yaml
groups:
  - id: g1
    name: "第一堆 · 定计划"
    order: 1              # 选填。不填时按分组之间的边自动排左右
```

**分组是标签，不是嵌套**：节点通过 `group` 字段引用分组 ID，**MUST NOT** 在 `groups` 里内嵌节点。

> **为什么不做成嵌套**：真做成一层套一层，跨堆的连线就画不出来了——而跨堆连线正是这张图最要紧的部分。用标签实现，自动读出和人工改都不会变难。

## 10. 校验：什么情况下拒绝出图

| 情况 | 处置 |
|---|---|
| 缺必填项 | **拒绝出图**，指名是整图层、哪个节点、还是哪条边的哪一项 |
| 条件必填项在触发条件成立时缺失 | **拒绝出图**（如标了会派子代理却没有清单、父子回传边没写 `screening`） |
| 边指向不存在的节点 | **拒绝出图**，指出是哪条边 |
| 出现双向边 | **拒绝出图**，提示拆成两条单向边 |
| 同一对节点同一方向多条边 | **拒绝出图**，提示合并为一条并用多个传递物表达差异 |
| 语法超出 §1 的子集 | **拒绝出图**，指出行号与不支持的语法 |
| 缺选填项 | **照常出图**，该处显示「未填写」 |

校验器 **一次报出全部问题**，不会遇到第一条就停。

怎么跑：

```bash
node scripts/validate.mjs <描述文件>              # 只校验，不出图
node scripts/validate.mjs <描述文件> --format json # 机器可读
node scripts/render.mjs   <描述文件> -o <输出.html> # 内部先校验，通过才出图
```

退出码：`0` 通过 · `2` 校验不通过 · `3` 语法错或文件读不了 · `1` 程序自身异常。
